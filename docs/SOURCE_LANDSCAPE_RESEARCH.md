# Source landscape: structured skill and technical competency evidence

Research snapshot: 2026-11-08

## Scope and decision standard

This review looks for sources that can help decompose professional skills and technical competencies into reusable axes: concept identity, hierarchy, prerequisite/composition, role/task/skill mappings, proficiency, co-occurrence, and demand. It records how the source can actually be acquired, the rights and operational limits on doing so, and what the resulting data can and cannot establish.

“Effort” means time or work actually invested by a person. None of the sources below directly measures individual effort. Occupational experience ranges, curriculum hours, profile/job-posting counts, and popularity are different quantities and must not be relabeled as effort.

Acquisition and reuse are separate questions. A public API, searchable website, or downloadable file does not itself authorize a redistributable corpus. Where a source's API terms are narrower than its file license, this review identifies the route whose reuse terms are documented. No source is marked implemented in the registry without a functioning collector.

## Feasibility and access terms are separate axes

A restrictive agreement is evidence about the stated contract terms; it is not proof that a dataset is technically unobtainable, and this review does not conclude whether a term is enforceable in a particular jurisdiction or fact pattern. Registry status `candidate` means there is a credible evidence surface and an acquisition path worth evaluating. It does not mean the path is authorized for corpus reuse. `blocked` should be reserved for a source with no practical acquisition route or no useful evidence surface after considering public, API, partner, licensed, and manual routes.

For sources with public but non-exportable interfaces, a technically feasible fallback may be a bounded capture of visible pages or aggregate charts, followed by timestamped snapshots and explicit coverage limits. That can answer narrower questions but does not magically become a complete or reproducible bulk feed. A documented API, partner export, written data license, or research agreement is the practical route to durable scale. For each source, separate the expected technical effort from the access and redistribution risk; do not infer one from the other.

The technical paths remain assessable even where a source's terms restrict the intended use. Record the route, expected coverage, limits, and terms risk separately so that permission, a narrower public-facing sample, or a decision to accept contractual exposure is a later project choice rather than a false claim of technical impossibility. Where available, official APIs and partner exports are usually the lowest-cost reproducible route; public interface collection remains a feasible but less complete fallback. This is not a legal determination about enforceability.

## Findings

1. The highest information gain comes from combining independent competency frameworks and technical ontologies, not accumulating more job-posting vocabularies. ESCO and O*NET give broad occupational context; NICE and DigComp contribute explicit competency structure; CSO adds an open, relation-rich technical topic ontology built independently from labor-market data. CS2023 adds expert curriculum composition but has higher extraction and redistribution cost.
2. Stack Overflow's tag dump/API and Developer Survey are complementary but not independent. The dump/API describe questions and tag co-occurrence; the survey captures self-reported use, aspiration, learning, and work context. The dump's old Archive.org route is not a safe assumption for current acquisition: Stack Overflow announced that quarterly dumps are hosted in-house and available through a member profile.
3. Package registries and official documentation contain strong technical composition evidence: declared dependencies, feature flags, TOC nesting, API symbols, and cross-references. Those edges describe software artifacts and publisher-authored documentation. They are not direct evidence that a person possesses a skill.
4. The major job-platform leads are technically more accessible than a binary “blocked” label suggests, but each exposes different evidence. LinkedIn documents a paginated Standardized Skills API, though the public access page does not establish the required entitlement and API terms constrain storage. Indeed publishes aggregate Skills Map views and partner SUID tables, but no complete public skills export was found. Dice's first-party unauthenticated MCP endpoint provides paginated structured job listings; it is not a skill taxonomy export, and bulk retention terms remain unclear. Treat these as candidates with separate technical-feasibility and terms-risk fields.
5. Lightcast has a detailed, evolving skill vocabulary and relationship model, but current API access is approval/contract based and the free access scope excludes some cross-dataset relationships and high-volume use. Its underlying evidence is substantially job-posting/profile-derived, so it should be compared as a market-model output rather than counted as independent confirmation.
6. To prevent false precision, every integration should preserve source version, retrieval date, exact endpoint/file, declared license, source-native identifiers, and the type of evidence represented. Crosswalks are mappings, not new independent observations.

## Ranked next five integrations

Scoring is a provisional ordinal planning aid, not measured probability. Each factor is 1–5. Information gain is weighted twice because the project needs new axes, not merely cheap volume. Linkage scores stable source identifiers, typed relations, and practical crosswalks to existing sources. Rights clarity scores whether the intended acquisition, retention, and redistribution scope is documented; API availability alone does not earn a high score. Implementation cost is scored with 1 = low and 5 = high; the formula rewards lower cost:

**Priority = (2 × information gain + source independence + reproducibility + linkage + rights clarity + (6 − implementation cost)) / 7**

Source independence is about the evidence origin, not whether the formats differ. A mapping copied from another framework receives no extra independence credit.

CS2023 is the strongest near-miss: its expert curriculum, knowledge units, learning outcomes, and instructional core hours add a curricular axis, but its extraction cost and redistribution gate lower its combined priority. The Stack Overflow Developer Survey and SFIA follow: the survey is available under ODbL but shares publisher and audience with Stack Overflow Q&A; SFIA has direct professional relevance and RDF/Excel files, but all use requires a license and the price/terms need confirmation. OpenAlex Topics is another low-cost scholarly classification lead, but its labels are inferred and its hierarchy partly maps to Scopus ASJC, making it less independent than CSO. The first technical-composition integration should then be one bounded package ecosystem, likely npm replication or a smaller PyPI classifier slice. Package dependencies are not a substitute for a skills taxonomy.

### Score notes and tradeoffs

- ESCO and O*NET are complementary, not interchangeable: ESCO is multilingual and European, while O*NET is U.S.-focused and unusually rich in occupational ratings, task statements, work context, and detailed work activities.
- NICE scores highly on cost and independence but is cybersecurity-specific. It should not be generalized to all software work.
- DigComp is a competence framework for citizens and lifelong learning. Its hierarchy and proficiency statements can supply reusable decomposition patterns, but occupational mapping requires a separate step.
- CSO ranks fifth because the versioned bulk files have high relation richness and low acquisition cost; its publication-derived topics still need to remain distinct from skill/competency evidence.
- Package registries likely have high marginal information gain for composition and dependency axes, but they are broad, noisy, and large. Scope one ecosystem and measure data volume before committing to a full replication.
- Lightcast and other job-market aggregators may improve market coverage, but they are neither low-cost nor independent of job/profile text.

## Source assessments

### Stack Overflow

#### Tag API and question dump

The Stack Exchange API exposes tag lists and tag metadata as well as endpoints for synonyms, related tags, and tag wikis. The related-tags result is derived from tag pairings in questions; it is a co-occurrence statistic, not a semantic parent-child relation. The documented default quota is 10,000 requests per day per key/IP, and traffic above 30 requests per second per IP can be dropped; clients must honor backoff and avoid repeating identical queries more than once per minute. This makes the API useful for smoke checks and incremental/small evidence, not for reconstructing the full question hypergraph. See the [API documentation](https://api.stackexchange.com/docs), [related tags endpoint](https://api.stackexchange.com/docs/related-tags), [tag endpoint](https://api.stackexchange.com/docs/tags), and [API throttling guidance](https://api.stackexchange.com/docs/throttle).

Stack Exchange content has historically been published through periodic data dumps, but route and access changed. Stack Overflow's [October 2024 community-product update](https://stackoverflow.blog/2024/10/03/community-product-update-knowledge-as-a-service/) says the quarterly dumps moved in-house and are accessed through each site's user profile. That announcement does not fully document a stable anonymous bulk endpoint, authentication flow, retention, or exact cadence. Archive.org remains a useful historical mirror but should not be treated as the current official acquisition path. Before an acquisition tranche, verify the live route and rights directly. User contributions are licensed under versioned CC BY-SA terms; see [Stack Overflow licensing](https://stackoverflow.com/help/licensing). API use is also subject to the separate [Stack Exchange API terms](https://stackoverflow.com/legal/api-terms-of-use).

The best data semantics remain: tag identities and synonyms; question-level unordered tag sets; answer/question text only where separately licensed and needed; and source-native counts/timestamps. Keep full hyperedges before deriving pair or 3–5 tag summaries. Related-tag API output is a convenient view over the same question corpus, so it is not an independent validation set.

#### Developer Survey

The annual survey is a distinct instrument with a public [results and files page](https://survey.stackoverflow.co/) and [methodology](https://survey.stackoverflow.co/2026/methodology). The 2026 site exposes chart data as structured JSON and identifies each chart's ODbL 1.0 license; anonymized response files are distributed through the survey results page and official survey repository. It covers technologies used and desired, roles, experience, learning, work context, and attitudes. It can support co-occurrence by respondent and subgroup, with respondent counts and survey-year identity.

This is a stronger evidence source for self-reported familiarity and aspiration than a Q&A tag count, but it remains self-report and selection-biased toward people reached through Stack Overflow channels. It is not a performance test, verified competency measure, or hours-worked dataset. The survey and Q&A corpus share publisher and audience, so treat them as related evidence. Preserve raw response values and question wording; do not harmonize away changes between annual instruments. Review [survey license information](https://questions.survey.stackoverflow.co/) and retain the ODbL obligations.

#### Mirrors and derived views

Google's documentation identifies a public BigQuery Stack Overflow dataset, and Stack Overflow announced marketplace availability in Snowflake. These are alternate access/distribution channels for the same underlying source, not independent evidence. BigQuery requires a Google Cloud project and charges for query bytes above the free allowance; Snowflake access may depend on Marketplace/account terms. Stack Exchange Data Explorer is a SQL-facing view over Stack Exchange data; its shared underlying corpus makes it a poor independent corroboration source. Use these routes for discovery or backup, not as separate corroborating sources.

### Wikidata

Wikidata is already implemented as an identity/context layer. The [official data-access page](https://www.wikidata.org/wiki/Help:Data_access) documents public APIs and database dumps; structured Wikidata content is CC0. Items have QIDs, properties, aliases, claims, qualifiers, references, and external identifiers. The [query service documentation](https://www.mediawiki.org/wiki/Wikidata_Query_Service/User_Manual) describes query-service limitations, including throttling and temporary blocks.

Its strongest contribution is concept disambiguation: technology names, aliases, classes, platforms, products, programming languages, and ecosystem relations. It is a community knowledge graph, not a maintained professional competency ontology. Many claims import or map information from other publishers. A Wikidata link to ESCO, O*NET, a software vendor, or a third-party taxonomy must be preserved as an identity mapping, not counted as independent evidence that the mapped concept is true or equivalent. Snapshot dumps are preferable to repeatable SPARQL queries for a corpus baseline.

### Occupational and market skill sources

#### ESCO

The European Commission's [download page](https://esco.ec.europa.eu/en/use-esco/download) provides free versioned datasets in RDF, Turtle, ODS, CSV, XML, and JSON-LD, in 28 languages. ESCO's [FAQ and reuse conditions](https://esco.ec.europa.eu/en/about-esco/faq) allow use and adaptation for any purpose with attribution and clear disclosure of modifications. Current at research time: v1.2.1; the download page displays last update `10/12/2025`, retained verbatim because its date format is not labeled. Downloads are free and require no API key; the public documentation reviewed does not state an API request quota, so versioned files are the reproducible bulk path.

ESCO distinguishes occupation concepts from skill/competence and knowledge concepts. It includes preferred/nonpreferred terms, multilingual labels, descriptions, occupation profiles, and mappings to ISCO-08. Concept URIs provide stable identity; download structure links language-specific labels to language-independent relations. This offers a real concept graph: broader/narrower relations and occupation-to-skill/knowledge relations. Pin the exact download release and language set. The web and local APIs use the ESCO OWL data model, but the download page warns that the existing local API is for reference and will be replaced; bulk files are the more reproducible starting point. Current future release cadence is not guaranteed.

Independence is relatively high as an institutional, stakeholder-developed European classification. Some ESCO concepts or mappings connect to other frameworks, including the e-CF and DigComp; mapped rows should not be double-counted as independent corroboration. ESCO classifies occupational relevance, not an individual's competence or effort. No fixed future release cadence is documented.

#### O*NET

The [O*NET Resource Center](https://www.onetcenter.org/database.html) currently publishes database 31.0 in CSV, Excel, JSON, SQL, and RDF and describes quarterly updates, with a primary release in Q3. The downloadable files are the recommended snapshot route. O*NET Web Services require registration and an X-API-Key. The [service terms](https://services.onetcenter.org/terms) permit throttling or suspension above 5 requests per second or 50,000 requests per day. The [current API manual](https://services.onetcenter.org/reference/start/overview) describes best-effort service, possible 429 responses, and no hard maximum enforced. Most database content is CC BY 4.0, but [license exceptions](https://www.onetcenter.org/license_agreements.html) apply to some content. Check the selected tables rather than assigning one blanket license to every file.

The O*NET-SOC occupation taxonomy covers U.S. work and organizes skills, knowledge, abilities, tasks, detailed work activities, work context, interests, work styles, education, training, and experience. Tables contain occupation-by-element ratings, including importance, level, frequency, and relevance where defined. Stable occupation, content-model element, scale, and task IDs support reconciliation between releases. This makes O*NET a dense source for task/competency composition and occupational context.

Ratings describe the importance or level of an element for an occupation; they are not ratings of a named person's proficiency. Education and experience fields are occupational descriptors, not effort totals. O*NET is independent evidence from ESCO, but both are designed to describe labor-market occupations and can share external frameworks or concepts.

#### NICE Framework

NIST publishes [NICE Framework Components](https://www.nist.gov/itl/applied-cybersecurity/nice/nice-framework-resource-center/nice-framework-current-versions) as JSON and XLSX, separately from the framework's SP 800-181 prose. The change log lists version 2.2.0 on 2026-04-28, while the current-version landing page still displays an inconsistent 2025 date. Use the change log for the release date and retain the inconsistency as source metadata.

Components include work-role categories, work roles, competency areas, and task, knowledge, and skill statements. Work roles and competencies have source IDs; relations connect roles/categories and, where supplied, work roles to tasks, knowledge, and skills. NIST's FAQ warns that these task/knowledge/skill alignments are not complete for every work role. The framework is cybersecurity-specific, versioned, free to download, and exceptionally convenient to snapshot. Verify the precise NIST reuse notice for any data copied into a redistributed product.

NICE supplies strong task and competency structure, but no universal proficiency score and no evidence of individual effort. Its independent institutional origin makes it a good contrast to occupational labor surveys.

#### DigComp

The JRC [DigComp 3.0 resources](https://joint-research-centre.ec.europa.eu/scientific-activities/key-competences-lifelong-learning/digital-competence-framework-digcomp/digcomp-30-resources_en) include a spreadsheet and structured JSON data alongside PDF/editable material. The 2025 fifth edition is released under CC BY 4.0 with attribution, change, and non-endorsement conditions. It has five competence areas, 21 competences, proficiency levels, competence statements, learning outcomes, and glossary entries. Learning outcomes distinguish knowledge, skills, and attitudes.

The framework is for citizen and lifelong-learning digital competence, not specifically for software jobs. That breadth can provide reusable decomposition axes and proficiency descriptors, but mapping to occupational roles requires separate evidence. The JRC publishes an errata list and says the published materials remain unchanged; therefore pin the original downloaded files and store the applicable errata as a separate overlay. The DigComp-to-ESCO work is a mapping project, not independent validation. No fixed future release schedule or API was found.

#### SFIA and European e-CF

[SFIA 9 documentation](https://sfia-online.org/en/sfia-9/documentation) includes PDF, Excel, and RDF Turtle files with skills, responsibility levels, generic attributes, and behavioral factors. This is directly relevant to professional digital work. SFIA also publishes prior editions, allowing version comparisons. However, its [license page](https://sfia-online.org/en/about-sfia/licensing-sfia/using-and-licensing-sfia) says SFIA use requires a license. Free browsing or downloadable files do not mean the extracted dataset is open for redistribution. Obtain the terms, price, version-change process, and data-retention permission before prioritizing a collector.

The European e-Competence Framework is a standards-based ICT-professional competency model. ESCO's [overview](https://esco.ec.europa.eu/en/about-esco/escopedia/escopedia/european-e-competence-framework-e-cf) reports 40 competencies; descriptions of EN 16234-1:2019 report 41. The difference appears edition/inventory-sensitive and should not be resolved by assuming one number: preserve the standard edition and exact source list. Public summaries show five e-competence proficiency levels and key knowledge/skill examples, while the normative standard is sold through standards bodies. No authoritative free bulk machine-readable acquisition route or general redistribution license was established. The e-CF is a promising independent comparison framework, but its licensing/acquisition gate keeps it behind open sources.

#### LinkedIn, Indeed, Dice, and Lightcast

These sources should not be collapsed into a generic “job-board skills taxonomy.” They expose different data products: standardized terms, aggregate demand charts, partner integration identifiers, public postings, and commercial model outputs. The terms can materially constrain reuse, but the term itself does not decide technical feasibility.

**LinkedIn.** Microsoft's [Standardized Data API Skills reference](https://learn.microsoft.com/en-us/linkedin/shared/references/v2/standardized-data/skills) documents GET, BATCH_GET, and GET_ALL. The GET_ALL response contains skill ID, standardized URN, localized standardized name, and locale, with a maximum of 50 items per response and a next-page link. This is a real low-volume enumeration route for a skill-name/ID catalog if the app receives the required entitlement. The [API access guide](https://learn.microsoft.com/en-us/linkedin/shared/authentication/getting-access) requires OAuth and says most permissions/programs need LinkedIn approval; its listed self-serve open permissions do not include Standardized Skills. The exact access product/approval route and rate quota were not established, and the Skills reference is dated 2023-05-08. The endpoint itself supplies no hierarchy or dependency relations. It should therefore be modeled as taxonomy/identity, not a competency graph.

Access to the endpoint does not settle persistence. LinkedIn's published [API terms](https://www.linkedin.com/legal/l/api-terms-of-use) restrict capture, caching, storage, and transformed data except where expressly permitted by those terms or additional terms. The current [User Agreement](https://www.linkedin.com/legal/user-agreement) states exceptions may be provided in separate writing, including research agreements, while prohibiting scraping/copying and use outside the APIs. The practical way to make a reusable LinkedIn corpus sustainable is a specific research agreement or data license covering the skill reference list, retention, snapshots, and derived redistribution—not merely an OAuth token. If API access is denied, a page-by-page public-profile sample is technically possible but incomplete, lacks the same stable skill catalog identifiers, is expensive to keep current, and carries a more direct terms/privacy risk.

**Indeed.** The public [Skills Map](https://www.indeed.com/skillsmap) exposes aggregate U.S. posting demand by industry and state. Its current methodology reports more than 3,000 skills, 48 categories, and 108 subcategories; a separate Hiring Lab snapshot reported 47 categories, so counts must be tied to a date rather than treated as a contradiction or a stable total. Indeed says the map uses a model built on its own taxonomy and classification system, and that the taxonomy evolves continuously. Public UI capture can reproduce the aggregate slices that users can select; it cannot recover the underlying postings or unrendered skill catalogue. A posting corpus can also be assembled technically from public job-result pages by enumerating query/location/page combinations, extracting visible posting IDs or canonical URLs and text, deduplicating, snapshotting, and reconciling edits/removals. No documented complete posting crawl/export was found, so result caps, region/query coverage, and page stability need empirical measurement; this route has higher change-tracking and reproducibility costs than an authorized feed.

Indeed's [Partner Docs](https://docs.indeed.com/job-sync-api/reference/occupations) provide structured HTML tables for a six-tier occupation hierarchy, and [SUID guidance](https://docs.indeed.com/integration-basics/understanding-suids) describes five-character identifiers for occupations, job types, and attributes, with search-attribute tables including skills. Those documents are machine-readable enough for a bounded reference-table snapshot, though they are partner integration documentation rather than a public skills dump. To scale from references and visible aggregates to posting-level evidence, the concrete route is an approved partner/data product or a licensed export; the technical alternative of repeated UI capture remains aggregate-only and less reproducible.

The [Indeed Developer Agreement](https://docs.indeed.com/legal-terms/developer-agreement-third-party) limits API use to the approved integration and restricts creating permanent copies/databases and distributing data without written permission. It also limits purpose and combining data. That is a material reuse gate, but it does not turn visible aggregate information or documented identifiers into a technical impossibility. Ask for permission that specifically covers a research dataset, retention period, derived statistics, and redistribution. Keep public UI snapshots separate from partner-provided records and preserve each query and visible date.

**Dice.** Dice's first-party [MCP documentation](https://www.dice.com/about/mcp) publishes an unauthenticated endpoint at `https://mcp.dice.com/mcp`, with a `search_jobs` tool, filters, page counts, page numbers, unique job IDs, descriptions, and a configurable 1–100 records per page. Its [setup article](https://www.dice.com/career-advice/how-to-connect-the-dice-mcp-server-to-your-ai-assistant) describes listings with required skill/technology information. The server documentation mentions HTTP 429 and recommends reducing request frequency, exponential backoff, and caching, but does not state a numeric quota. A bounded reproducible study is technically feasible: define a role/keyword/region/time sampling frame; retain the exact request, retrieval time, raw response, and page metadata; deduplicate by job ID; then derive posting-level term co-occurrence. Search pagination is not proof of complete historical or current-market coverage, and the MCP interface does not export Dice's underlying skills ontology.

The [Dice site terms](https://www.dice.com/about/terms-and-conditions) prohibit unapproved tools/processes for navigating, searching, or storing site information; prohibit manual or automatic data mining/reproduction; and restrict AI/model use of site information for research as well as commercial use. Dice's first-party MCP is explicitly provided for programmatic job search, but its public docs do not resolve whether repeated archival sampling and redistribution of derived corpora are allowed. For a durable public corpus, seek clarification or a research license. For feasibility assessment, the endpoint is a real technical route; the terms and endpoint's query coverage are separate uncertainties.

**Lightcast.** Lightcast remains the strongest commercial market-taxonomy lead. Its [skills taxonomy page](https://lightcast.io/taxonomies/skills-taxonomy) describes more than 34,000 concepts organized into category, subcategory, and skill tiers with unique IDs and definitions. [API access documentation](https://docs.lightcast.io/lightcast-api/docs/api-access) says public-good access is free but approval-based; commercial or production use requires a commercial license. The free API scope limits extraction to 50 requests per month and excludes other taxonomies and cross-dataset relationships. The [Skills v10 methodology](https://kb.lightcast.io/en/articles/7216059-lightcast-skills-taxonomy-methodology-and-skills-v10) says the taxonomy derives from hundreds of millions of postings, resumes, and profiles, and refreshes every four weeks; v10 was released 2026-10-23. It has a category hierarchy and dynamic supply/demand relationships.

Lightcast combines taxonomist curation with aggregated market evidence, so it is useful as a labor-market model but not independent confirmation of the underlying posting/profile vocabulary. It may map to O*NET, which also does not create a second independent assertion. Before prioritizing an integration, get written answers on complete extraction, stable IDs, historical snapshots, quotas, prices, and retention/redistribution.

### Independent technical taxonomies and curricula

#### CS2023

The [ACM/IEEE-CS/AAAI CS2023 site](https://csed.acm.org/) publishes the report and structured knowledge-area pages. It defines 17 knowledge areas containing knowledge units and topics, identifies CS Core and Knowledge Area Core topics, gives illustrative learning outcomes, and allocates core instructional hours. These axes are valuable because they express what expert curriculum authors think a computing graduate should encounter, independent of job ads or question volume.

Acquisition is through official HTML and report PDFs; no complete public API or machine-readable export was found. Report editions and web page structure must be pinned. The report is copyrighted by its sponsoring organizations; [ACM's permissions terms](https://www.acm.org/publications/policies/copyright-policy) and report notices should be reviewed before redistribution. A research mapping may be possible with limited excerpts or permission, but the repository should not publish a full transformed taxonomy until rights are resolved. Core hours mean curriculum instructional allocation, not time invested by each learner.

#### ACM Computing Classification System

The [ACM CCS 2012 page](https://www.acm.org/publications/class-2012) describes the subject taxonomy integrated into ACM Digital Library indexing. It classifies computing research concepts, not skills, roles, or proficiency. ACM author instructions say authors can select concepts in the [CCS interface](https://dl.acm.org/ccs/ccs.cfm) and export XML for the selected concepts. A first-party ACM DL RDF/XML asset path has also been observed at [acm_ccs2012-1626988337597.xml](https://dl.acm.org/pb-assets/dl_ccs/acm_ccs2012-1626988337597.xml), but our research fetch received HTTP 403; anonymous bulk availability is therefore unresolved rather than established as impossible. If that path is unavailable in ordinary access, automated or manual traversal of the visible selector could recover the hierarchy, but enumeration cost, identifier stability, and completeness would need a pilot.

ACM's [how-to guide](https://authors.acm.org/binaries/content/assets/publications/article-templates/ccs-howto-v6-12jan2015.pdf) describes a six-level tree. The 2012 system is polyhierarchical and concept assignments in articles are publisher/indexer tagging, not independent semantic edges between skills. The source is now a candidate because an official selector and first-party XML route exist; redistribution still needs copyright review or a permission grant. Do not apply IEEE Xplore API terms to ACM CCS or treat a 403 from a research fetch as a rights or access ruling.

#### Additional open technical taxonomies

**Computer Science Ontology (CSO).** The Open University [CSO downloads portal](https://cso.kmi.open.ac.uk/downloads) offers versioned N-Triples, OWL, Turtle, and CSV bulk files. Version 3.5 was released 2025-07-29 and contains about 15,000 topics linked by 166,000 semantic relationships. The [CSO model documentation](https://cso.kmi.open.ac.uk/about) describes eight relation types, including `superTopicOf`, `relatedEquivalent`, `preferentialEquivalent`, `contributesTo`, `owl:sameAs`, and `schema:relatedLink`, plus label/type statements. The [FAQ](https://cso.kmi.open.ac.uk/faq) states CC BY 4.0. This is a particularly strong candidate for reusable technical meta-axes because it distinguishes hierarchy, equivalence, and contribution rather than flattening all relatedness into one edge.

The ontology was generated with Klink-2 over the Rexplore dataset of roughly 16 million publications, then some links were reviewed by experts. That makes it independent of job-market and package data, but still a scholarly-topic model with publication-source bias—not a competency or effort measure. Preserve the exact release and every relation predicate; do not reinterpret its `contributesTo` edge as a prerequisite.

**OpenAlex Topics.** The official [Topics documentation](https://help.openalex.org/data/topics/) currently describes 4 domains, 26 fields, 252 subfields, and 4,516 topics. The public [OpenAlex API](https://help.openalex.org/api/) supports entity lookup, list/search/filter/page, and says basic use is free without a key; a free key increases the daily budget. Topic IDs use a `T` prefix. Works may receive up to three model-inferred topics, which are research-aboutness assignments rather than human-authored skill tags.

OpenAlex says the topics were built by clustering a citation network, naming clusters with a language model, and mapping the hierarchy to Scopus ASJC categories. The result provides an evolving scholarly taxonomy and document-level topic co-occurrence at low technical cost, but shares research-publication bias with CSO and borrows part of its hierarchy from ASJC. OpenAlex states its data are CC0. Preserve retrieval date, topic IDs, assignment model semantics, and schema version; do not interpret assignment as demonstrated competency or employer demand.

#### IEEE Technology Navigator

IEEE's [TechNav FAQ](https://technav.ieee.org/faq/) describes 8,800+ engineering/technology topics derived from the IEEE Thesaurus, API endpoints for topic search/detail and linked resources, and annual taxonomy updates. It requires an API key requested from IEEE. Public alphabetical browsing is also available. The API route is technically plausible, but the FAQ does not settle enumeration/pagination, API quotas, ID stability, versioned archive access, or reuse rights. These are questions to send to the TechNav team after obtaining the key; the absence of a public quota is not evidence that bulk acquisition is impossible.

TechNav is a candidate with an approval/key gate. Its technical vocabulary is independent of job-market evidence; resource counts and links are based on IEEE's own content catalogue. IEEE Xplore's API has separate terms and is not evidence of TechNav's terms. Obtain TechNav-specific answers before retaining/re-publishing a complete corpus.

#### Technical documentation structures

Official documentation is a source family, not one uniform dataset. Prefer first-party Git repositories and structural files over HTML scraping:

- [Microsoft Learn documentation repositories](https://github.com/MicrosoftDocs) commonly expose TOC.yml, article frontmatter, API reference symbols, and DocFX build artifacts. Navigation changes with documentation commits; licenses vary by repository and may separate documentation from code.
- [MDN content](https://github.com/mdn/content) and its sidebars encode product and web-platform subject hierarchy. Check the repository's CC BY-SA documentation license and distinguish code-example licenses.
- [Python documentation sources](https://github.com/python/cpython/tree/main/Doc) are authored alongside CPython and built with Sphinx; generated indexes and inventories can identify modules and references. Pin the release and inspect license notices.

Documentation can expose authored domain structure, containment, sequence, and explicit cross-references. It rarely states that a link is a prerequisite. A navigation parent should be modeled as a publisher's information architecture, not a transitive conceptual subsumption edge. A product's own documentation is independent of Stack Overflow questions, but not independent from the vendor's product ontology. Repository commit histories make these sources reproducible if rights and versions are retained.

#### MIT OpenCourseWare and course catalogs

[MIT OpenCourseWare](https://ocw.mit.edu/) exposes course pages and downloadable course materials, often including prerequisites, syllabi, topic/week sequences, assignments, and readings. No complete general-purpose catalog API was found. Course numbers and archived term versions provide usable identities, but per-course and per-asset licensing varies. MIT's current [terms and license page](https://ocw.mit.edu/pages/privacy-and-terms-of-use/) presents CC BY-NC-SA 4.0 as the default, while some materials or third-party assets are reserved or otherwise restricted. Review each selected course and resource; a site-wide default must not be applied indiscriminately.

Course prerequisites and ordered topic sequences provide curriculum composition, while posted hours or workload estimates are sporadic and not actual personal effort. Instructor selection and course availability create selection bias. The ACM/IEEE-CS/AAAI CS2023 framework is more coherent and machine-readable in concept, but MIT OCW can supply richer implementation-level examples and course artifacts when item licensing permits.

### Package registries

Package registries are not skill ontologies. They contain names, versions, publisher-provided descriptions, keywords/classifiers, manifests, and dependency declarations. They supply technical identity and explicit composition between software artifacts. Registry data is often cross-published and publisher-entered; package dependencies do not imply that one package's users know how to use another. Package download or popularity counts are noisy usage signals, not worker demand or effort. Keep registry metadata rights separate from the licenses of downloadable package artifacts.

- **npm.** The first-party [registry replication API](https://github.com/npm/registry/blob/main/docs/REPLICATE-API.md) documents CouchDB-style replication and a changes feed; [npm terms](https://docs.npmjs.com/policies/open-source-terms/) permit replication of public-registry data through public APIs but prohibit unreasonable request volume and call five million monthly requests clearly unreasonable. Package/version IDs and manifest dependencies form useful composition edges. Keywords and descriptions are publisher supplied. Incremental replication is a better acquisition model than repeated full scans.
- **PyPI.** The official [JSON API](https://docs.pypi.org/api/json/) returns project/release metadata, digests, and Core Metadata; [API policy](https://docs.pypi.org/api/) states there is currently no edge rate limit but discourages thousands of requests in minutes and reserves the right to block irresponsible use. Trove classifiers and keywords are submitted by projects; [classifier documentation](https://pypi.org/classifiers/) describes the controlled values, but assignment is not centrally validated. No general blanket metadata license or complete downloadable snapshot was established.
- **NuGet.** The [V3 registration resource](https://learn.microsoft.com/en-us/nuget/api/registration-base-url-resource) gives package/version metadata and framework-specific dependency groups. The chronological [Catalog resource](https://learn.microsoft.com/en-us/nuget/api/catalog-resource) records pushes, relisting, deprecation, vulnerability changes, and delete events. [Rate-limit documentation](https://learn.microsoft.com/en-us/nuget/api/rate-limits) says V3 search is currently not rate-limited, while other surfaces have quotas and may return 429/403. Package IDs, versions, dependency groups, and event timestamps are strong incremental-ingest anchors.
- **crates.io.** Cargo documents the [sparse and git indexes](https://doc.rust-lang.org/cargo/reference/registry-index.html), which contain versioned package metadata and dependencies; the [crates.io API policy](https://github.com/rust-lang/rfcs/blob/master/text/3463-crates-io-policy-update.md) sets one request per second and asks for an identifying User-Agent. The index is a more suitable bulk source than issuing API calls or downloading crate archives. Metadata includes keywords, categories, dependency features, and package/version IDs; tags remain publisher supplied.
- **Maven Central.** Sonatype documents a [Search REST API](https://central.sonatype.org/search/rest-api-guide/) for coordinates and artifact metadata. POM files may expose group/artifact/version, licenses, dependencies, scope, and optionality. Requests may be rate limited and aggressive use can be blocked; use the published [429 guidance](https://central.sonatype.org/faq/429-error/) and published repository endpoints. There is no standardized skill taxonomy in POM tags, and metadata/artifact rights remain distinct.

A first implementation should be bounded and resumable. npm's replication feed is unusually reproducible for incremental metadata but potentially broad in volume. A PyPI classifier-focused slice may be cheaper for a first experiment, but it will underrepresent skills not expressed in classifier vocabulary. Compare the first snapshot and reconciliation cost before expanding to all registries.

## Cross-source independence and interpretation rules

Use these distinctions in later analysis:

- **Taxonomy**: a source-authorized category, hierarchy, or controlled term system (ESCO, O*NET, NICE, DigComp, SFIA, e-CF, ACM CCS, IEEE).
- **Identity**: stable source ID, aliases, external ID, package coordinate, or URL (Wikidata, ESCO URIs, O*NET IDs, package coordinates).
- **Composition/dependency**: explicitly declared dependency, prerequisite, area/unit/topic membership, or task-to-skill relation (package manifests, course prerequisites, curriculum nesting, selected NICE mappings).
- **Co-occurrence**: terms observed together in a question, respondent, profile, posting, or package manifest. Preserve the unit of observation and do not confuse this with semantic relatedness.
- **Competency/proficiency**: framework statements about expected skill, task, knowledge, or level. These are source-defined standards or models, not direct assessments of an individual.
- **Market demand**: postings, profiles, or employer signals. This is a market observation, affected by duplicated ads, platform coverage, extraction models, and recency.
- **Effort**: only an explicit record of actual time/work invested by a person. None of these sources supplies that at adequate individual granularity.

Where two sources exchange mappings, model the mapping provenance explicitly. For example, ESCO mappings to an e-CF concept do not produce two independent assertions. Wikidata's imported external IDs are identity bridges. Lightcast's mapping to O*NET is a crosswalk. Stack Overflow's related tags, BigQuery public table, and Stack Exchange dump are derivative views of the same underlying community data.

1. Recheck the current Stack Exchange dump acquisition route and its exact access/authentication conditions. Keep the existing acquisition-script work separate from this research branch.
2. For each open data source, save the source-native release identifier, download URL, retrieval timestamp, file hash, source license text/version, and any errata/change log alongside acquired files.
3. For gated market/platform sources, separate the access request from the reuse request: LinkedIn needs the Standardized Skills entitlement plus any research agreement for storage/derived redistribution; Indeed needs partner/data scope plus a research-use carve-out or export license; Dice needs clarification whether MCP results may be sampled, archived, and redistributed as derived evidence; IEEE TechNav needs an API key, enumeration semantics, quotas, and TechNav-specific reuse terms; Lightcast needs the current extraction, price, snapshot, and license terms. Do not infer rights from public visibility or an API key.
4. For copyrighted curriculum sources, separate private research access from public transformed output. CS2023 and e-CF are high-value but need rights-resolved acquisition.
5. For all “effort” questions, pursue a separate evidence design. Curriculum hours, job experience requirements, popularity, and proficiency levels are not person-level time investment.
6. Before committing to package registry replication, estimate snapshot size, incremental update volume, metadata retention, duplicate handling, and the exact subset needed to answer the meta-axis question.
